# Как работает расчёт стоимости обучения текстовых LLM за 2025 год

## 1. Что является объектом расчёта

Считается стоимость обучения публичных текстовых LLM, представленных на
Hugging Face репозиториями с весами и датой создания в 2025 году.

Считаются не репозитории сами по себе, а уникальные training runs. Один training
run может быть опубликован в нескольких репозиториях, форматах или зеркалах —
его стоимость должна учитываться только один раз.

Результат является оценкой стоимости вычислений в H100-equivalent, а не суммой
реальных счетов компаний.

## 2. Первичные критерии попадания

Репозиторий попадает в рассматриваемый рынок, если одновременно выполняются
условия:

1. репозиторий публично доступен на Hugging Face;
2. `createdAt` находится между 1 января и 31 декабря 2025 года, UTC;
3. в репозитории есть распознанные веса модели;
4. модель относится к обработке естественного языка;
5. модель не относится к исключённым non-text категориям.

Ограничений по числу параметров, likes, downloads или популярности нет.

## 3. Что полностью исключается

Из количества целевых моделей и из стоимости исключаются:

- image и diffusion-модели;
- text-to-image и image-to-image;
- video и text-to-video;
- VLM, vision-language и multimodal-модели;
- computer vision;
- audio, speech, TTS и music-модели;
- protein, DNA, genomic, chemical и другие модели неестественного языка;
- репозитории без весов;
- приватные, удалённые и недоступные репозитории;
- закрытые модели, веса которых не опубликованы на Hugging Face.

Картинки, видео и VLM не учитываются даже как строки с нулевой стоимостью: они
вообще не входят в рынок текстовых LLM.

## 4. Как определяется тип модели

Для каждого репозитория выполняется одно и то же дерево решений. Проверки идут
строго сверху вниз. Как только сработало более сильное правило, предварительный
тип считается определённым.

### Шаг 4.1. Проверка на quantization или conversion

Репозиторий получает тип `quantized`, если найден хотя бы один из признаков:

- Hugging Face `baseModels.relation` равен `quantized`;
- tags содержат `gguf`, `ggml`, `gptq`, `awq`, `exl2`, `quantized`,
  `compressed-tensors`, `bitsandbytes`, `4-bit` или `8-bit`;
- library равна `mlx`, `onnx` или `openvino`;
- имя содержит GGUF, GPTQ, AWQ, EXL, quantized, INT4, INT8, FP8, MLX, ONNX,
  OpenVINO, TensorRT, CoreML, convert или conversion;
- имя похоже на автоматическую HF/Transformers-конверсию или встроенную копию
  другого repository ID.

После этого модель остаётся в статистике репозиториев, но стоимость нового
обучения ей не назначается.

### Шаг 4.2. Проверка на merge

Тип `merge` назначается, если:

- `baseModels.relation` равен `merge`;
- tags содержат `model-merge` или `merge`;
- имя репозитория содержит отдельный компонент `merge` или `merged`.

Merge не получает стоимость нового обучения.

### Шаг 4.3. Проверка явной связи с upstream-моделью

Если Hugging Face metadata прямо сообщает:

- relation `adapter` — назначается `adapter`;
- relation `finetune` — назначается `finetune`.

### Шаг 4.4. Проверка training tags

Тип `finetune` назначается при tags:

- `generated_from_trainer`;
- `trl`;
- `sft`;
- `dpo`;
- `grpo`;
- `rlhf`;
- `rl-swarm`;
- `genrl-swarm`;
- `unsloth`.

Тип `adapter` назначается при tags `peft`, `lora`, `qlora`, metadata вида
`base_model:adapter:*` или компонентах `lora`, `qlora`, `adapter`, `peft` в
имени репозитория.

### Шаг 4.5. Проверка поля base_model

Если metadata или cardData содержит непустое поле `base_model`, `baseModel` или
`base_models`, модель считается производной.

- adapter-связь уже была поймана предыдущим правилом;
- все остальные такие репозитории предварительно получают `finetune`.

То есть наличие ссылки на чужую base-модель никогда не приводит к типу `base`.

### Шаг 4.6. Проверка имени на fork/mirror

Тип `fork` назначается, если имя содержит отдельный компонент:

- `abliterated`, `ablation`;
- `uncensored`, `unfiltered`, `ungated`, `unlocked`;
- `heretic`, `blasphemer`;
- `repack`, `reupload`, `mirror`;
- `dequantized`, `pruned`, `sliced`, `patched`;
- `checkpoint`, `ckpt`, `step` или `stage` с номером;
- UUID-подобное автоматическое имя;
- известный формат технического артефакта/копии.

Такой репозиторий остаётся в категории fork и не получает стоимость нового
pretraining.

### Шаг 4.7. Проверка имени на производное обучение

Тип `finetune` назначается, если имя содержит отдельный компонент:

- `finetune`, `fine-tuned`;
- `sft`, `dpo`, `grpo`, `rlhf`;
- `instruct`, `chat`;
- `distilled`;
- `reasoning`, `thinking`;
- `aligned`, `adapted`;
- `post-training`, `cpt`.

### Шаг 4.8. Остаточный base-кандидат

Если ни одно правило выше не сработало, репозиторий получает предварительный
тип `base`.

Это означает только следующее:

> Metadata не показала, что репозиторий является известной производной моделью,
> конверсией, merge или очевидным fork.

На этом этапе стоимость ещё не начисляется.

### Шаг 4.9. Повторная классификация по model card

Полный текст карточки может исправить предварительный тип.

Если в карточке найдено опубликованное training time/cost и тот же фрагмент
явно говорит о LoRA/QLoRA/PEFT/adapter, остаточный `base` меняется на `adapter`.

Если фрагмент говорит о fine-tuning, instruction tuning, post-training,
continued pretraining, domain adaptation, distillation, SFT, DPO, RLHF или GRPO,
остаточный `base` меняется на `finetune`.

### Шаг 4.10. Повторная классификация локальной LLM

Каждый остаточный base-кандидат с известным числом параметров отправляется
локальной LLM вместе с metadata и текстом карточки.

Если LLM с `high` confidence и проверенной дословной цитатой возвращает:

- `independent_base` — окончательный тип `base`;
- `continued_pretraining` или `finetune` — окончательный тип `finetune`;
- `adapter` — окончательный тип `adapter`;
- `fork_or_mirror` — окончательный тип `fork`;
- `quantized` — окончательный тип `quantized`;
- `merge` — окончательный тип `merge`;
- `non_text` — репозиторий полностью удаляется из text-выборки.

Medium-confidence решение не может уверенно переклассифицировать модель в
производную категорию. Medium `independent_base` остаётся base-кандидатом, но
его стоимость допускается только в upper estimate.

Low/unknown ничего не подтверждает и стоимости не даёт.

### Итоговое правило типа

В упрощённом виде алгоритм выглядит так:

```text
если non-text признаки                      -> удалить из text-рынка
иначе если quantization/conversion          -> quantized
иначе если merge                            -> merge
иначе если relation=adapter                  -> adapter
иначе если relation=finetune                 -> finetune
иначе если trainer/SFT/DPO/RLHF tags         -> finetune
иначе если PEFT/LoRA/adapter tags или имя    -> adapter
иначе если заполнен base_model               -> finetune
иначе если fork/mirror признаки             -> fork
иначе если finetune/instruct/chat имя        -> finetune
иначе                                       -> base-кандидат

затем прочитать model card
затем применить high-confidence local-LLM correction
затем проверить independent-pretraining evidence
только после этого решать, начислять ли стоимость
```

## 5. Как проверяются base-кандидаты

Для каждого base-кандидата анализируется model card.

Сначала обычный парсер ищет:

- прямое заявление об обучении с нуля;
- обучение с random initialization;
- описание самостоятельного pretraining;
- указание upstream/base checkpoint;
- признаки continued pretraining или fine-tuning;
- число pretraining tokens;
- total и active parameters;
- training dates.

Затем неоднозначные base-кандидаты проверяет локальная LLM. Она не считает
стоимость, а только определяет происхождение весов:

- самостоятельный base training;
- continued pretraining;
- fine-tune;
- adapter;
- fork/mirror;
- quantization;
- merge;
- non-text;
- недостаточно данных.

Для положительного решения LLM обязана привести дословную цитату из model card.
Если цитаты нет в карточке, решение не принимается.

У решения есть confidence:

- `high` — сильное подтверждение;
- `medium` — вероятное подтверждение;
- `low` — данных недостаточно.

Low-confidence решения стоимость не получают.

## 6. Как определяется принадлежность к 2025 году

Основной критерий — `createdAt` репозитория в 2025 году.

Если model card явно сообщает training year:

- при наличии 2025 run остаётся в расчёте;
- если указан только другой год, run исключается из стоимости 2025 года.

Год, предложенный LLM, принимается только если этот год буквально присутствует
в проверенной цитате из карточки.

Если фактический год обучения не опубликован, используется год создания
репозитория. Это отдельное допущение расчёта.

## 7. Когда base-модель получает стоимость

Base-модель получает стоимость только при одновременном выполнении условий:

1. это текстовая LLM;
2. это не fork, mirror, merge или quantization;
3. есть подтверждение самостоятельного pretraining;
4. известно число параметров;
5. модель относится к 2025 году по правилам выше;
6. training run не является дубликатом другого учтённого run.

Base-кандидат без подтверждения самостоятельного pretraining остаётся в
статистике рынка, но не получает стоимость.

## 8. Формула стоимости base-модели

Используются следующие константы:

- GPU: NVIDIA H100;
- производительность: 989 TFLOPS;
- полезная эффективность: 40%;
- стоимость: $1.85 за GPU-час;
- fallback token budget: 20 токенов на параметр.

Формула:

```text
training_FLOPs = 6 × N_effective × T

GPU_hours = training_FLOPs /
            (989 × 10^12 × 3600 × 0.4)

cost_USD = GPU_hours × 1.85
```

Где:

- `N_effective` — число параметров, участвующих в вычислениях на один токен;
- `T` — число токенов pretraining.

## 9. Как выбирается число токенов

Если карточка явно сообщает фактическое число pretraining tokens, используется
оно.

Если число токенов не опубликовано, применяется fallback:

```text
T = 20 × N_total
```

Для обычной dense-модели без опубликованного token budget итоговая формула:

```text
cost_USD = 155.881361644759 × parameters_billions²
```

Пример для dense 7B:

```text
155.881361644759 × 7² ≈ $7,638.19
```

Это оценка по единой формуле, а не утверждение о фактически оплаченном счёте.

## 10. Как считаются MoE-модели

Если у MoE опубликовано число active parameters:

- `N_effective` берётся по active parameters;
- fallback token budget считается по total parameters.

Формула становится:

```text
training_FLOPs = 6 × N_active × (20 × N_total)
```

Если active parameters не опубликованы, используется total parameters.

Отдельно сохраняется более жёсткий sensitivity-сценарий с `N_total²`, но он не
является основной central-оценкой.

## 11. Как считаются fine-tune и adapters

Для fine-tune, continued pretraining, LoRA, QLoRA и adapters полный
base-pretraining fallback не применяется.

Их стоимость учитывается только если model card сообщает собственный compute
или прямую стоимость обучения.

Если прямо опубликована стоимость обучения, используется она.

Если опубликованы длительность и число GPU:

```text
GPU_hours = training_hours × GPU_count
cost_USD = GPU_hours × hourly_rate
```

Если ставка опубликована, используется опубликованная ставка. Если ставка не
указана, используется $1.85 за GPU-час.

Если количество GPU не указано, предполагается один GPU и это отмечается как
допущение.

Если compute time или прямая стоимость не опубликованы, модель не получает
стоимость. Никакой произвольный процент от стоимости base-модели не применяется.

## 12. Что не получает стоимость нового обучения

Стоимость равна нулю или остаётся пустой для:

- fork и mirror;
- reupload;
- abliterated/uncensored fork;
- повторного checkpoint одной траектории;
- quantization;
- конверсии формата;
- merge;
- fine-tune или adapter без reported compute;
- base-кандидата без подтверждения независимого pretraining;
- base-кандидата без числа параметров;
- low/unknown решения локальной LLM;
- дубликата уже учтённого training run.

Fork, quantized и merge могут оставаться в статистике количества репозиториев,
но не увеличивают стоимость обучения.

## 13. Как удаляются дубли

Один training run должен быть посчитан только один раз.

Дубли определяются по следующим признакам:

1. одинаковый hash model card или evidence;
2. одинаковый reported training run;
3. одинаковый canonical training run от локальной LLM;
4. одинаковое семейство, владелец и точное число параметров для checkpoint
   trajectory;
5. одинаковое нормализованное имя и точное число параметров для очевидных
   зеркал между разными владельцами;
6. датированные snapshots одной fine-tune/adapter trajectory.

У дубликата стоимость очищается. В расчёте остаётся один канонический
репозиторий.

Разные размеры одной семьи не склеиваются. Например, независимо опубликованные
7B, 32B и 70B считаются отдельными runs.

## 14. Как формируются три итоговые суммы

### Lower

В lower входят:

- base-runs с прямым детерминированным evidence самостоятельного pretraining;
- fine-tune/adapters с опубликованным compute или стоимостью;
- только уникальные runs после дедупликации.

### Central

В central входят:

- всё из lower;
- high-confidence independent-base решения локальной LLM с проверенной цитатой.

Central — основная оценка.

### Upper

В upper входят:

- всё из central;
- medium-confidence independent-base решения локальной LLM с проверенной
  цитатой.

Low-confidence и unknown не входят ни в одну сумму.

Всегда должно выполняться:

```text
lower ≤ central ≤ upper
```

## 15. Как правильно интерпретировать результат

В итоговой формулировке одновременно указываются:

- lower в долларах и число runs;
- central в долларах и число runs;
- upper в долларах и число runs;
- общее количество публичных text-LLM репозиториев;
- количество уникальных training runs, получивших стоимость.

Количество репозиториев нельзя называть количеством обученных моделей. Forks,
adapters, quantizations, merges и mirrors создают отдельные репозитории, но не
обязательно являются новыми полными training runs.

Итоговая оценка включает только GPU compute по принятым правилам. Она не
включает:

- inference;
- CPU, storage и сеть;
- покупку и подготовку данных;
- зарплаты команды;
- неудачные эксперименты;
- закрытые частные кластеры;
- модели, не опубликованные на Hugging Face.

## 16. Критерии, которые нужно согласовать

| Вопрос | Используемое правило |
|---|---|
| Какие модели? | Только публичные text LLM с весами |
| Какой год? | `createdAt` в 2025; явный другой training year исключает run |
| Картинки/video/VLM? | Полностью исключены |
| Ограничение размера? | Нет |
| Порог популярности? | Нет |
| Base без evidence? | В рынке остаётся, стоимость не получает |
| Fork/mirror? | Стоимость нового обучения не получает |
| Quantized/merge? | Стоимость нового обучения не получает |
| Fine-tune/adapter? | Только при reported compute/cost |
| Нет compute у derivative? | Стоимость не оценивается |
| Цена GPU по умолчанию | $1.85 за H100 GPU-час |
| Token budget по умолчанию | 20 токенов на параметр |
| MoE | Active × tokens от total |
| High LLM confidence | Входит в central |
| Medium confidence | Только upper |
| Low/unknown | Не входит в стоимость |
| Дубли | Один training run считается один раз |
| Разные размеры семьи | Считаются отдельно |
| Основная цифра | Central вместе с диапазоном lower–upper |
